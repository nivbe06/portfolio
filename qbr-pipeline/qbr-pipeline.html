Session Logs to QBR Insights

Gigabytes of session and integration logs, per customer, per month, turned into a quarterly business review a CSM can present without editing. The design rule underneath everything below: the warehouse does the reduction, the LLM does the language. Every number a customer sees is computed in SQL. The model never counts, never aggregates, never detects.

1  /  Why the naive path is not a near miss

"Send the logs to an LLM" is not expensive, it is arithmetically impossible. Worth drawing once, because it sets the size of the reduction the rest of the system has to achieve.

2  /  The reduction funnel

Six stages, each cheaper to scan than the last, except one that deliberately holds flat. Every stage is ordinary warehouse work, which is exactly why it scales: this is what SQL engines are built for and what LLMs are not. These figures are measured, not estimated, counted from a working implementation that generates 2.18 million events across four accounts and six quarters.

~46,000×

Roughly 100 million tokens of raw log become a 2,153-token payload for a complete three-section QBR. At frontier-model pricing that is a few cents per account per quarter. The LLM is a rounding error; warehouse compute is the real cost line. That is the argument for putting the reduction first, not a side effect of it. In the implementation the ratio is enforced by a dbt test, so the funnel is an invariant rather than a slide.

3  /  Architecture

Read top to bottom. The band a component sits in decides what it is allowed to do: everything above the semantic layer is deterministic SQL, everything below it is generated language, and the semantic layer is the membrane that neither side crosses uninvited.

4  /  Where the LLM does not go, and why

The interesting half of the design is the exclusions. Each of these is something an LLM could do and shouldn't, because a deterministic component does it better, cheaper, or verifiably.

Excluded

Anomaly detection

Rolling z-score, threshold rules and dbt tests in rpt_. Cheap, auditable, reproducible across 20M events. A model scanning for anomalies is the non-deterministic, unverifiable version of a solved problem.

Excluded

Any arithmetic

No counting, no aggregation, no percentage. The model is handed finished numbers and asked for sentences. It cannot invent a figure because it is never asked to produce one.

Excluded

Free SQL on production

Text-to-SQL is the least reliable component in a system this shape, so it gets the smallest possible surface: metric queries against the semantic layer only, read-only, tenant-scoped.

Excluded

Deciding what matters

Materiality is business logic with a known weighting: revenue impact, contracted goals, paid-feature adoption. Ranked in SQL before the model sees anything.

Included

Section selection

The wizard is deterministic by default: the CSM sets account, period and segment as parameters. The model picks from a fixed registry of QBR bundles. Free-form natural language is the escape hatch, not the main path.

Included

Narrative

"Coupon redemption on the Q3 winback campaign fell 22% against Q2, concentrated in Enterprise, while session volume grew 8%" is presentable. A table of numbers is not. This is the one thing only a model does well.

5  /  Two things that make it defensible

Guardrail

Salience ranking

The brief asks for anomalies worth discussing with the customer. A z-score returns roughly 40 flags a quarter and most are noise. Ranking by business materiality cuts that to three or five before generation. Statistically significant and worth ninety seconds of a QBR are different tests.

Guardrail

Grounding check

A deterministic post-check extracts every figure from the generated narrative and asserts it exists in the structured input. Anything unmatched is rejected and regenerated. Hallucinated numbers in front of a customer is the failure mode that ends the product, so it gets a hard gate rather than a prompt instruction.

Property

The pipeline is also a PII firewall

Raw logs carry profile attributes, identifiers and cart contents. By rpt_ the data is aggregate and carries no individual identity, so nothing personal ever reaches the model. A GDPR-relevant property that falls out of the architecture for free, which matters for EU enterprise accounts.

Loop

CSM edits are the quality signal

Packs are generated on demand, so the figures are current as at the review rather than as at a batch job that ran weeks earlier. A human still reviews before a customer sees it; the wizard is an edit surface rather than a generate-and-hope one. Captured edits are the cheapest available evaluation data.

7  /  It runs

This is not only a design. The pipeline above is implemented and every number on this page is measured from it: a generator producing 2.18 million Talon.One-shaped events across four accounts and six quarters, a dbt DuckDB DAG of 22 models and 65 tests, a self-hosted Cube semantic layer, and a /create-qbr skill that produces the pack.

Enforced

The PII firewall is a test

assert_no_pii_in_rpt.sql inspects the published layer's actual columns and fails the build if any personal identifier reaches it. The claim cannot quietly stop being true.

Enforced

The funnel is a test

assert_reduction_ratio.sql fails if the published layer outgrows its row budget. If the reduction stops holding, the build breaks rather than the assumption.

Enforced

The tenant boundary is code

Every base cube is public: false and query_rewrite appends a tenant filter from the caller's signed token before planning. Four checks prove it: a base cube refused, a cross-account query returning nothing, an unsigned token rejected.

Measured

The ranker earns its place

For one account the ranker received eight flagged movements. A notification-volume change at z = +3.6 was dropped; a coupon redemption collapse at z = −3.6 surfaced. Identical statistical significance, opposite decisions, because only one of them costs the customer money.
